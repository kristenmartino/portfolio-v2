## Overview

SpecialtyPulse is a healthcare analytics project that uses Databricks and Airflow to process public Medicare data for reimbursement and procedure reporting.

The project includes metric definitions, example access policies and verification scripts. The public dashboard uses bundled reimbursement samples, synthetic sales and usage data, and illustrative security-check results.

## Problem framing

Three reporting requirements shaped the project:

1. **Metric definitions:** Document each metric’s calculation, source and aggregation so reports use consistent definitions.
2. **Role-based access:** Apply access policies to the datasets used by the dashboard and verify the results for each role.
3. **Data handoff:** Document expected columns, suppression rules and validation thresholds for pipeline outputs.

PySpark notebooks process CMS files through raw, staging and reporting layers in Delta Lake. Raw values are loaded as text; staging converts types, handles suppression and normalizes specialty labels.

Reporting tables aggregate results by specialty, procedure and year. New tables undergo row-count checks before replacing the previous version.

Airflow orchestrates the tasks and retries failed steps. A shared Python module defines columns, valid years, suppression rules and taxonomy mappings.

## Metric definitions and access controls

The project documents metric calculations, alternative definitions and reasons for the selected formulas.

It includes Domo access-policy configuration and verification scripts. Domo access was through a free trial that has since ended, so I can no longer run live policy checks.

The public dashboard runs as a standalone React app using representative data.

## The dashboard

The [public React dashboard](https://specialtypulse.kristenmartino.ai) uses sample and synthetic data across five pages:

- **Market Intelligence:** Reimbursement comparisons by specialty.
- **Procedure Detail:** Payment and volume trends by procedure.
- **Pipeline Intelligence:** Synthetic deals compared with reimbursement scores.
- **Adoption Tracking:** Example dashboard-usage metrics.
- **PDP Governance:** Example access policies and verification results.

The dashboard includes specialty drill-downs and on-screen metric definitions. Chart callouts and summaries are computed from the displayed data. An optional AI selection suggests an evidence-linked review task when API access is configured.

## Implementation notes

- **Table replacement:** The drop-and-rename step can briefly leave the reporting table unavailable.
- **Domo uploads:** The transfer script uses a single dataset upload. Chunked uploads are documented as a future extension.
- **Access verification:** Live Domo checks require an active instance and credentials. Without credentials, CI checks script syntax. The public dashboard displays sample results.
- **Scoring:** The pressure index uses project-defined weights that have not been validated against sales outcomes. Pressure-weighted pipeline is an illustrative comparison.

## Summary behavior

The dashboard summary computes observations directly from the displayed data, including every specialty's active pipeline amount and share. Its optional AI step chooses a review task from a fixed set of evidence-linked options. The app rejects responses that do not match an available task and its supporting observations; model-authored claims are not displayed.

The governance summary is computed from the example policy matrix. Sample checks do not establish live security.

## What I would validate next

Before using this approach for operational decisions, I would test complete source releases, verify access with each intended role, connect a real CRM dataset and evaluate the pressure score against outcomes. Stakeholder roles and approval workflows in the documentation are design examples, not recorded executive sign-off.
